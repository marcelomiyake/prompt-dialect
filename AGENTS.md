# AGENTS.md

Instructions for AI coding agents (Claude Code, Codex, and others) working in this repository. Humans are welcome to read along.

## What this project is

prompt-dialect checks the prompts people write to AI coding tools. As you type, it underlines mistakes and offers one-click fixes from a fast, cheap model (Claude Haiku 5.5 by default). On request, it rewrites the prompt to follow Anthropic's prompting guidance for the model the session uses.

Claude Code is the first tool it supports, as a mod (a Claude Code plugin with a hooks module). The repository root is the plugin (`.claude-plugin/plugin.json`, `hooks/`, `types/index.d.ts`, `icon.png`) and also its own marketplace (`.claude-plugin/marketplace.json`, with `source: "./"`). Other tools and IDEs come later, so the business logic is kept apart from every tool's API.

## Architecture: the dependency rule

The code follows Domain-Driven Design and Clean Architecture. Dependencies point inward only:

```
src/adapters/<tool>/  ──▶  src/core/application/  ──▶  src/core/domain/
   (Claude Code mod)          (use cases, ports)         (entities, value objects, rules)
```

- `src/core/domain/`: the model. `TextSpan`, `TextChange`, `Suggestion`, the `GrammarReview` aggregate, `TargetModel`, `PromptingGuide` and its catalog, and `PromptImprovement`. It imports nothing outside `domain/`.
- `src/core/application/`: the use cases `CheckGrammar` and `ImprovePrompt`, the prompts sent to the model, reply parsing, and the `LanguageModel` port in `ports/`. It imports only from `domain/` and `application/`.
- `src/core/index.ts`: the core's public surface. Adapters import from here, never from deeper files.
- `src/adapters/claude-code/`: the Claude Code mod. `register.tsx` is the composition root and the only file that touches the engine's `$`. `presenter.ts` (view model), `band.tsx` (drawing), `decorations.ts`, `pastes.ts` (the paste placeholders Claude Code folds into the box), `review-state.ts` and `settings.ts` are free of `$`.

Rules that keep it that way:

- Never import from `src/adapters/` inside `src/core/`, and never import `claude-code` in `src/core/`.
- `src/core/` runs inside the Claude Code mod sandbox, which has no DOM and no Node. Use only standard ECMAScript 2023 there: no `node:` modules, no `process`, no `Buffer`, no timers.
- A new tool is a new folder under `src/adapters/` that implements `LanguageModel` and draws the core's results with that tool's UI. Do not change the core to fit one tool.
- A new Claude model's prompting guidance is a new entry in `src/core/domain/prompting-guides.ts`, with its `source` URL. The catalog picks the closest guide for any model id, so no other code changes.

## Claude Code mod constraints

The mod's static analysis (`claude plugin validate`) rejects code that breaks these rules:

- Write every engine call in full: `$.noun.method(...)`. Pass `$` only to functions declared at the top level of `register.tsx`, or to `read` and `update` from `claude-code`. Never store `$` or a namespace of it in a variable.
- `$.state` references take literal `plugin` and `key` values. The mod keeps all its state in one value, `session` (see `plugin-state.d.ts`). Change it with `update($, session, fn)`, never with a read followed by a separate write.
- Event names passed to `on` are string literals.
- `hooks/register.js` and `types/index.d.ts` are generated by `npm run build`. Never edit them by hand. They are committed, because a marketplace install uses them as is. Rebuild after every change under `src/`.

The API's type declarations are generated per Claude Code build and are not committed. Run `npm run types:sync` to copy them into `types/claude-code/` before type-checking. It finds them in `.claude-plugin/types/` after you load the mod once with `claude --plugin-dir .`, or at the path in `$CLAUDE_CODE_TYPES`.

## Commands

| Task                                            | Command                                                       |
| ----------------------------------------------- | ------------------------------------------------------------- |
| Install                                         | `npm ci`                                                      |
| Format, or check formatting                     | `npm run format`, `npm run format:check`                      |
| Unit tests (vitest)                             | `npm test`                                                    |
| Unit tests with coverage                        | `npm run test:coverage`                                       |
| Copy the Claude Code API types                  | `npm run types:sync`                                          |
| Type-check source and tests                     | `npm run typecheck`                                           |
| Bundle the mod                                  | `npm run build`                                               |
| Bundle and copy to a hot-reloaded mods folder   | `node scripts/build-claude-code-plugin.mjs --mirror <dir>`    |
| Validate the mod                                | `npm run validate:plugin`                                     |
| Run the mod's tests inside Claude Code's engine | `npm run test:plugin`                                         |
| Everything above, in order                      | `npm run verify`                                              |
| SonarQube Cloud analysis                        | `SONAR_TOKEN=… npm run sonar` (after `npm run test:coverage`) |
| Re-record the README demo (needs VHS)           | `vhs docs/demo.tape`                                          |

Tests come in two kinds:

- `tests/**/*.spec.ts(x)`: vitest. The behaviour, with a fake engine (`tests/support/fake-engine.ts`) and a scripted model. These produce the coverage SonarQube Cloud reads.
- `tests/engine/*.test.ts`: `claude plugin test`, which runs every `*.test.ts` under the root. They load the bundle in the real engine and check that each surface accepts the trees the band draws.

## SonarQube quality gate

Project `marcelomiyake_prompt-dialect` in the SonarQube Cloud organization `marcelomiyake`: <https://sonarcloud.io/project/overview?id=marcelomiyake_prompt-dialect>. CI (`.github/workflows/ci.yml`) analyzes every push to `main` and every pull request. Automatic Analysis is off, because only CI uploads coverage.

Work is done only when the gate passes with these targets:

- Zero open issues of any type or severity: bugs, vulnerabilities, code smells.
- Every security hotspot reviewed.
- Coverage of 80% or more, overall and on new code. The suite currently covers about 99% of lines.
- Duplication on new code of 3% or less.

How to keep it there:

- Fix the cause of an issue. Do not add `// NOSONAR`, rule exclusions, or coverage exclusions to make a number pass. If a rule is a real false positive, mark it in SonarQube Cloud with a written reason, and say so in the pull request.
- Only `src/**/*.d.ts` (type declarations) and `scripts/**` (build tooling) are excluded from coverage. Do not widen that list.
- Write a test with every behaviour change, and run `npm run test:coverage` before pushing.
- Before pushing, check the code for the issues SonarQube most often raises here: nesting deeper than four functions (S2004), the same string literal three or more times (S1192), cognitive complexity over 15 (S3776), nested ternaries (S3358), regular expressions open to catastrophic backtracking (S5852), and functions that return different types (S3800).
- After CI runs, read the result with `sonar list issues -p marcelomiyake_prompt-dialect` or in the SonarQube Cloud UI, and fix anything new before merging.

## Commit messages: Conventional Commits

Every commit follows [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/):

```
<type>(<optional scope>): <description>

<optional body>

<optional footer(s)>
```

- **type**: one of `feat` (a new feature), `fix` (a bug fix), `docs`, `style` (formatting only), `refactor` (neither fixes a bug nor adds a feature), `perf`, `test`, `build` (build system or dependencies), `ci`, `chore`, `revert`.
- **scope**: the area changed: `core`, `domain`, `application`, `claude-code`, `guides`, `build`, `ci`, `deps`, `docs`.
- **description**: imperative mood, lowercase, no trailing period, about 72 characters at most. For example: `feat(claude-code): show the fix in context when a chip is hovered`.
- **body**: what changed and why, wrapped at 72 characters, separated from the subject by a blank line.
- **breaking changes**: add `!` before the colon (`feat(core)!: rename CheckGrammar outcome statuses`) and a `BREAKING CHANGE: <what to change>` footer.
- **footers**: `Refs: #12`, `Co-Authored-By: ...`, in `token: value` form.

Keep one logical change per commit, and do not mix a refactor with a behaviour change. A commit that changes `src/` also includes the rebuilt `hooks/register.js`.
